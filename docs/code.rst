*************
C++ API
*************

This section contains a documentation of the C++ classes and functions. All 
classes and functions in the documentation reside in the namespace ``grunk``. 
To use grunk's C++ API, you have to include the header `grunk.h`.

grunk supplies two modes of operation, that will be denoted as 
:ref:`static mode <grunk-core>` and :ref:`dynamic mode <grunk-dynamic>`. Use the static mode of grunk, if you know all the types you want to use at 
compile time. Use the dynamic mode of grunk, if you want to use types and functions provided
by plugins which are loaded at run time. In this case, grunk falls back to its
-dynamic type system, see also the :ref:`design principles <design-dynamic-sublanguage>`
-section of this documentation.

The static mode is the basis of grunk, implemented in ``grunk::core``.

.. _grunk-core:

``grunk::core``
===============  

The core of grunk consists of the ``action`` function together with 
``Feature`` class.

A ``Feature`` represents any kind of feature in the feature tree.
Given any kind of *referentially transparent* function and some input features
from the feature tree, the function ``action`` registeres the evaluation
of the given function for the given features as input in the feature tree.

.. code-block:: cpp

   grunk::Feature<double> l(3.3).with_id("l");
   grunk::Feature<double> r(2.2).with_id("r");
   auto res = grunk::action(std::add, l, r);
   std::cout<<res.value()<<std::endl; // evaluate the result, thus triggering the calculation

Using grunk in this way is also called *static mode*, because all types and functions are known at compile time.

.. _grunk-dynamic:

``grunk::dynamic``
================== 

Just like in static mode, the usage of grunk revolves around ``DynamicFeature``\s
and an overload of the ``action`` function.

The main difference is that dynamic mode depends on a valid LUA state, that is owned 
by a ``grunk::state`` instance. The state is used to store all registered types and functions, and to execute the LUA code that is generated by grunk.

We will call the grunk::state instance grunk and employ C++'s context aware name resolution.

A `DynamicFeature` wraps a `grunk::object`, which is the main type in grunk's dynamic mode. A `grunk::object` can hold any kind of value, and can be used to represent any kind of feature in the feature tree.

.. code-block:: cpp

   grunk::state grunk;

   grunk.register_function("add", std::add); // register the function "add" in the grunk state, so that it can be used in the feature tree   

   auto l = grunk.feature(3.3).with_id("l");
   auto r = grunk.feature(2.2).with_id("r");
   auto res = grunk.action("add", l, r).with_id("o");
   std::cout<<res.value().as<double>()<<std::endl; // evaluate the result, thus triggering the calculation


The types and functions must be registered from plugins loaded at run time, see also 
the :ref:`plugin section <grunk-plugin>` of this documentation or the 
:ref:`corresponding section<using-plugins>` under Usage.

.. _grunk-plugin:

``grunk::plugin``
=================

This section documents ``grunk::plugin``'s native-plugin loader: ``grunk::plugin::load_native``,
``grunk::plugin::load_script``, the fixed ``grunk_plugin_info``/``grunk_plugin_register`` ABI, and
the ``GRUNK_PLUGIN_EXPORT`` export macro. The plugin-authoring entry points that live directly on
``grunk::state`` (``begin_plugin``, ``load_compiled_plugin``, ``load_lua_plugin_script``/
``load_lua_plugin_file``, ``register_external_type``, ``PluginInfo``) are documented as part of
:ref:`grunk::dynamic <grunk-dynamic>` instead, since they're declared there. See the
:ref:`plugin section <using-plugins>` under Usage for a tutorial covering all three plugin kinds.
